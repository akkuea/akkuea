# Pilot Whitelist Data Handling

This document describes how investor identity data is collected, stored, encrypted, accessed, and deleted in the Akkuea pilot whitelist system. It applies specifically to the **pilot whitelist** (revenue-participation token investors) and does not cover the general KYC system.

---

## Data Collected

| Field | Type | Purpose | Storage |
|-------|------|---------|---------|
| `wallet_address` | Stellar public key (G...) | Unique investor identifier; on-chain whitelist key | Plaintext (required for on-chain operations) |
| `full_name` | String (max 255) | Legal name for identity verification | **Encrypted at rest** (AES-256-GCM envelope) |
| `id_type` | Enum (passport, national_id, drivers_license) | Government ID type | Plaintext |
| `id_reference` | String (max 255) | Government ID number | **Encrypted at rest** (AES-256-GCM envelope) |
| `document` | File (PDF/JPG/PNG, ≤10MB) | Government ID scan for operator review | **Encrypted at rest** (AES-256-GCM) |
| `status` | Enum (pending, approved, rejected) | Application state | Plaintext |
| `rejection_reason` | Text (nullable) | Operator-provided rejection reason | Plaintext |
| `created_at`, `updated_at`, `reviewed_at` | Timestamps | Audit trail | Plaintext |

---

## Where Data Lives

### Database (PostgreSQL)
- Table: `pilot_whitelist_requests`
- Columns `full_name` and `id_reference` store **plaintext copies** for operational convenience (display in admin UI, search).
- Columns `full_name_encrypted` and `id_reference_encrypted` store the **envelope-encrypted** versions (see Encryption below).
- Column `document_url` stores the relative path to the stored document (e.g., `kyc/Gxxxx/uuid.pdf`).
- Column `document_encryption_key` reserved for future per-document key rotation (currently unused; document encryption uses the storage provider key).

### Document Storage
Configured via `STORAGE_PROVIDER`:

| Provider | Location | Encryption at Rest |
|----------|----------|-------------------|
| `local` (default) | `KYC_UPLOAD_DIR` / `STORAGE_LOCAL_DIR` (default: `./uploads/kyc`) | Optional via `STORAGE_ENCRYPTION_KEY` (AES-256-GCM per file) |
| `s3-compatible` | S3 / R2 / MinIO bucket (`STORAGE_S3_BUCKET`) | Optional via `STORAGE_ENCRYPTION_KEY` (AES-256-GCM per file) or bucket-level SSE-S3 |

**Both providers encrypt each file individually with a unique IV and auth tag.** The storage encryption key (`STORAGE_ENCRYPTION_KEY`) is a base64-encoded 32-byte key. Without it, files are stored in plaintext (development only).

### Document Access
- Documents are **never served directly**. Operators request a signed, time-limited URL via `GET /pilot/whitelist/document/:requestId` (requires `x-internal-api-key`).
- Signed URLs expire in **1 hour** (configurable via code).
- The URL is generated by the storage provider:
  - Local: tokenized path with expiry timestamp, validated on access.
  - S3-compatible: AWS pre-signed URL via `@aws-sdk/s3-request-presigner`.
- Non-operators (investors, public) have **no access** to document URLs or decrypted PII.

## Encryption

### Field-Level Encryption (full_name, id_reference)
- **Algorithm**: AES-256-GCM (envelope encryption)
- **Key Encryption Key (KEK)**: Derived from `FIELD_ENCRYPTION_KEY` (or `STORAGE_ENCRYPTION_KEY` if not set) via scrypt with fixed salt (`akkuea-field-encryption-salt`).
- **Data Encryption Key (DEK)**: Random 256-bit key generated per field per row.
- **Storage Format** (JSON in `full_name_encrypted` / `id_reference_encrypted`):
  ```json
  {
    "ciphertext": "base64",
    "encryptedDek": "base64",  // DEK wrapped with KEK (IV + authTag + wrapped DEK)
    "iv": "base64",            // 96-bit IV for data encryption
    "authTag": "base64",       // 128-bit GCM auth tag
    "version": 1               // Key version for rotation
  }
  ```
- **Key Rotation**: Supported via `rotateFieldKey()` which re-wraps the DEK with a new KEK without re-encrypting the plaintext.
- **Migration**: Existing plaintext rows can be encrypted in-place by running `encryptPlaintextField()` on each value and writing to the encrypted columns.

### Document Encryption (Storage Layer)
- **Algorithm**: AES-256-GCM per file
- **Key**: `STORAGE_ENCRYPTION_KEY` (base64-encoded 32 bytes)
- **Per-file**: Unique 96-bit IV, 128-bit auth tag prepended to ciphertext.
- **Provider-agnostic**: Both `LocalStorageProvider` and `S3CompatibleStorageProvider` implement the same encryption logic.

## Who Can Read What

| Actor | Can Read Plaintext PII? | Can Read Encrypted PII? | Can Access Documents? |
|-------|------------------------|------------------------|----------------------|
| Investor (self) | No | No | No |
| Operator (via dashboard) | Yes (decrypted on demand in review modal) | Yes (DB access) | Yes (via signed URL, 1hr expiry) |
| API Admin (internal key) | Yes (via internal endpoints) | Yes | Yes (via signed URL) |
| Database Backup Holder | **No** (only sees ciphertext) | Yes (ciphertext only) | **No** (files encrypted) |
| S3 Bucket Lister | **No** | N/A | **No** (objects encrypted) |
| Application Logs | **No** (PII never logged) | N/A | N/A |

**Critical**: Database backups, bucket listings, or copied files **cannot** reveal investor PII without the encryption keys.

## Retention and Deletion

### Rejected / Withdrawn Requests
- **Retention Period**: `WHITELIST_RETENTION_DAYS_REJECTED` days (default: 90) from `updatedAt` (rejection timestamp).
- **Job**: `WhitelistRetentionJob` runs daily (configurable via `WHITELIST_RETENTION_POLL_INTERVAL_MS`).
- **Actions on Expiry**:
  1. Delete document from storage (if `document_url` exists).
  2. Anonymize `full_name` → `[REDACTED]`, `id_reference` → `[REDACTED]`.
  3. Clear `full_name_encrypted`, `id_reference_encrypted`, `document_url`, `document_encryption_key`.
  4. Keep `wallet_address`, `id_type`, `status`, `rejection_reason`, timestamps for audit trail.
- **Dry Run**: Set `dryRun: true` in job config to log actions without executing.

### Approved Requests
- **Never purged or anonymized**. Required for on-chain auditability and investor record.
- Documents retained indefinitely (or until manual operator action).

### Data Subject Deletion Request (Operator-Initiated)
- **Endpoint**: `DELETE /pilot/whitelist/:requestId` (operator only, requires `x-internal-api-key`).
- **Action**: Same as retention job (delete document, anonymize PII).
- **Use Case**: GDPR/CCPA "right to be forgotten" for rejected applicants.

## Operational Procedures

### Key Rotation (Field Encryption)
1. Generate new `FIELD_ENCRYPTION_KEY` (base64-encoded 32 bytes).
2. Deploy new key to environment (rolling restart).
3. Run migration script: for each row, call `rotateFieldKey(encrypted, oldKey, newKey)` and update `full_name_encrypted` / `id_reference_encrypted`.
4. Verify decryption works with new key.

### Key Rotation (Storage Encryption)
1. Generate new `STORAGE_ENCRYPTION_KEY`.
2. **Re-encrypt all existing objects** (download, decrypt with old key, encrypt with new key, upload). This is a heavy operation; plan maintenance window.
3. Deploy new key.
4. Verify document access works.

### Disaster Recovery
- **Database**: Standard PostgreSQL backup/restore. Encrypted fields are opaque strings; no special handling.
- **Documents**: Backup the bucket/filesystem. Files are individually encrypted; without `STORAGE_ENCRYPTION_KEY` they are unreadable.
- **Keys**: Store `FIELD_ENCRYPTION_KEY` and `STORAGE_ENCRYPTION_KEY` in a secrets manager (Vault, AWS Secrets Manager, etc.). **Loss of keys = permanent data loss for encrypted fields/documents.**

## Compliance Notes

- This system implements **minimum defensible** identity handling for a single-ally pilot.
- It is **not** a general-purpose KYC engine.
- Legal instrument classification (Known Risk #2) is open; encryption and retention policies are designed to be defensible across common jurisdictions.
- No data is shared with third parties. All processing is on Akkuea infrastructure.
- Audit logs (via `AuditService`) record operator actions (approve/reject/view document) with actor wallet and timestamp.
